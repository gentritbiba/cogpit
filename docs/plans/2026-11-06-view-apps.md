# View apps: interactive views as small React apps

Status: all five phases built on `feat/view-apps` (iOS on the iOS repo's `feat/view-apps`). Follows the
inline-HTML MVP in v3.6.0. How the built parts work: `docs/interactive-views.md`.

## Goal

An agent builds a view as a small React app from a ready-made component kit,
saved as files it can edit and rebuild when the result is not what the user
wanted. Every view is kept and listed in the sidebar for later reference. The
engine stays small, modular and strict about its inputs.

## Decisions (owner, 2026-11-06)

- **The computer that owns the view builds it.** That is the machine running
  the session. It compiles the source into one finished HTML document. Every
  other client (a hub device, a share guest, the iPhone) fetches that document
  and only displays it. No client compiles anything.
- **Storage lives on that same computer**, grouped per project.
- **iOS displays the built document** in a web view and runs no build step.

The page's own interactive code (a slider moving a chart) still runs where it
is shown, inside the sandbox, because interaction cannot round-trip to the
host. "The host handles the runtime" means it does all the building, resolving
and checking. The viewer only runs a finished, self-contained page.

## How it works

```
agent writes files ──► cogpit-session view build ──► version N (source + built HTML)
                                                     │
reply carries  ```cogpit-view                        │
               sales-funnel@3                        │
               ```                                   ▼
desktop card / hub / share / iOS ──► GET /api/views/<id>/v/3 ──► sandbox
```

### Files

```
~/.cogpit/views/<view-id>/
  view.json          title, project, sessionId, versions
  app/App.tsx        default export is the root component
  app/**             more .tsx/.ts/.jsx/.js/.css/.json files, relative imports
  versions/<n>/      immutable: index.html and files.json
```

- Ids are unique on the computer, so a reply's `<id>@<n>` finds its view
  without knowing the project. The project (the session's folder, with
  worktrees folded into their parent via `shared/worktreePath.ts`) is recorded
  in `view.json`, and the sidebar groups by it.
- `view-id` is lowercase words joined by single hyphens, at most 48
  characters. Source files are plain files inside `app/` (lstat, no symlinks),
  at most 40 files and 4 folders deep; 512 KB per source file, 2 MB per JSON
  file, 4 MB in total.
- Data is a JSON file the app imports (`import data from "./data.json"`).
- The agent edits `app/` with its normal Write and Edit tools. An update is a
  small edit plus a rebuild, not a rewritten block.

### Agent loop

Run through the existing `cogpit-session` forwarder, which already gives the
server the caller's session:

- `cogpit-session view new <id> --title "…"` creates the folder with a
  starter `App.tsx` and prints its path.
- `cogpit-session view build <id>` compiles, reports errors as
  `file:line:col message`, stores version N and prints the fence to paste.
- `cogpit-session view list` lists the project's views and their versions.

The build catches syntax errors, unknown imports and unknown kit exports
before the user ever sees the view.

### Reply fence

A `cogpit-view` block whose whole body is `<id>@<version>` references a stored
view. Any other body is a legacy inline HTML view and keeps rendering the way
it does today, so older transcripts keep working. The new skill teaches only
stored views.

An old reply keeps showing the version it named. When a newer version exists,
the card offers it ("v4 available"), so editing a view never rewrites what an
earlier message showed.

### Build (`server/views/`)

| Module | Job |
| --- | --- |
| `store.ts` | folders, `view.json`, versions, path and size limits |
| `build.ts` | transform each source file, resolve imports |
| `kit.ts` | the prebuilt kit modules and the specifiers each provides |
| `document.ts` | the final HTML: base CSS, frame kit, loader, kit and app modules |
| `routes/views.ts` (in `server/routes/`) | fetch a version; later list, pin, delete |

- **Transform:** `sucrase` (pure JS, small, fast) turns TSX/TS into CommonJS.
  It runs the same under Electron's utility process and the standalone Bun
  server. It must also go into `packages/cogpit-cli/package.json`.
- **Modules without a bundler:** every module travels as JSON in one script
  tag, and a loader of about 25 lines runs them with `require`, `module` and
  `exports` through indirect eval with a `sourceURL`, so errors name the
  agent's file and line. No import maps, no blob URLs and no network, so the
  same HTML runs unchanged in a desktop iframe and in an iOS web view.
- **Kit modules** are prebuilt at app build time (esbuild, already a dev
  dependency) into `generated/view-kit/`. The build includes only the modules
  the app imports. The React API is Preact underneath, so the base kit
  (Preact, compat and `cogpit/ui`) is about 34 KB and a small view's page
  about 50 KB. The advanced modules and raw libraries come only when imported.
- **Cache:** a version's built HTML is written once and served with an ETag.
  Rebuilding unchanged source reuses the existing version.

### The kit: a light base, optional advanced pieces, and free custom code

The kit exists to make common views quick. It must never limit what an agent
can build. When nothing in it fits, the agent writes its own component right
there in `app/`, and that is a normal path, not a fallback. Kit components and
custom ones mix freely.

**Base (`cogpit/ui`, in every view, a few KB):** shadcn-style looks on
plain elements, with no Radix or other headless library underneath. Most
pieces are a styled element plus a class, so they stay small and easy for an
agent to read and extend:

- layout: `Stack`, `Row`, `Grid`, `Card`, `Section`
- text: `Heading`, `Text`, `Muted`, `Code`
- data: `Stat`, `Table`, `Badge`, `Progress`
- input: `Button`, `Slider`, `Select`, `Toggle`, `Tabs`, `Input`
- helpers: `useTheme`, `themeColor`, `useAnimationFrame`, `ask`, `formatValue`

Every base piece forwards `className` and `style` and renders a real element,
so an agent can restyle it or drop down to plain JSX at any point. The theme
tokens and base CSS from the MVP still style raw HTML, so a view written
without the kit still looks native.

**Advanced (included only when imported):**

- `cogpit/charts`: `LineChart`, `BarChart`, `AreaChart`, `ScatterChart`,
  `PieChart`, drawn as themed SVG on d3 scales (no charting library). They
  accept children for custom marks, so an agent can add annotations or layers
  without leaving the chart.
- `cogpit/math`: `Tex` (KaTeX, MathML output; not `Math`, which would hide
  the global `Math` in the agent's module)
- `cogpit/scene`: `Scene3D` around Three.js with orbit controls
- the raw libraries: `d3`, `katex`, `three`

**Free code:** any React, SVG, canvas, WebGL, CSS animation or Web Worker the
agent writes. The only limits are the sandbox's (no network) and the size
limits above.

Each kit module is a folder with its code and a short doc snippet. The skill's
component table is generated from those snippets, the way
`sync-cogpit-skill` already works, so adding a module is one folder plus one
registry line. Reuse `@cogpit/plugin-ui` styling where it fits, but not its
dependencies if they would make the base heavier.

A root error boundary shows a readable error inside the view, and the card
keeps its "Ask to fix" button.

### Showing a view

The sandbox contract stays the same: an opaque origin, no network, and a
parent that trusts nothing the page posts.

- **Desktop:** the card fetches the built HTML through `authUrl`, which adds
  the hub prefix for a remote device's session. It then posts the HTML into
  the existing `/api/views/shell/v1` frame. Theme, resize, error, `open` and
  `ask` messages work as today.
- **Hub:** a remote session's view request goes to `/hub/<device>/api/views/…`,
  so the device that owns it builds and serves it. Nothing new beyond testing
  the proxy path.
- **Share guests:** the allowlist admits `GET /api/views/shell/v1` and
  `GET /api/views/<id>/v/<n>`; the route serves a page only when the shared
  session made the view.
- **iOS (`ios/` repo):** a card fetches the HTML with the app's own auth, then
  loads it into a `WKWebView` with `loadHTMLString(html, baseURL: nil)`, a
  non-persistent data store and a content rule list that blocks every load.
  A script message handler carries resize, error, `open` and `ask`, and the
  theme is injected before the page runs.

### Sidebar: Views

- Per project, newest first: title, session, version, updated time.
- Opening a view shows it in a side panel with a version picker. "Open in
  panel" on the timeline card does the same.
- Pin, rename and delete. Nothing is deleted automatically.
- Backed by `GET /api/views?project=` on the session's machine. Through the
  hub, the list shows the active device's views.

## Phases

1. **Store, build and card (local), built:** files, `view new|build|list|show`,
   sucrase, loader, Preact and the base kit, fetch route, card for
   `id@version` fences with source and version switch, skill rewrite. The
   team edition keeps stored views admin-only (members still load the shell),
   and `view` commands need an admin, until phase 3.
2. **Advanced kit, built:** `cogpit/charts` (line, area, bar, scatter, pie),
   `cogpit/math` (`Tex`), `cogpit/scene` (`Scene3D`), raw `d3`/`katex`/`three`
   imports, and the skill's kit section generated from each module's `doc`.
   The skill mentions inline pages only for agents that cannot run `view`.
3. **Remote, built:** a view belongs to the session that made it; routes
   authorize that session, so team members and share guests reach a view as
   they reach its session. Team `ROUTE_POLICIES` make `/api/views` authed with
   the shell session-free, the access matrix probes every view route, and
   `view` commands follow session access. Deleting leaves a tombstone.
4. **Sidebar and panel:** list, panel, version picker, pin, rename, delete.
5. **iOS card** in the `ios/` repository.

Rough size: one to two weeks. The kit is the largest part.

## Open

  answer: yes for the owner, while share guests only see views of the shared
  session.
- Retention for views whose sessions are archived. Proposed answer: keep them
  until deleted, since they are small.
