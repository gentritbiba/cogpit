Cogpit Team Edition

One Cogpit on a shared box, a login for every person using it. Your team drives Claude Code, Codex, and GitHub Copilot CLI sessions through the browser; the machine, the CLI logins, and the MCP connections stay in one place.

Personal edition unchanged cogpit-server only Local accounts Admin / member roles Hub-compatible

01What this is

Cogpit ships as one binary with two editions. Nothing about your desktop app changes — personal edition is the default and behaves exactly as it always has. Team edition is a flag you set on the headless server.

personal

What you use today

Desktop app or local server. One user, no login on the machine itself, everything unlocked.

team

The business box

Named accounts, everyone logs in, roles gate the dangerous surfaces. Standalone server only.

The important consequence: in team edition "local" is no longer trusted. On a personal box, any process on the machine can talk to Cogpit without a password. That is fine on your laptop and unacceptable on a shared server, so team edition requires a session for every request — including from a browser running on the box itself.

One agent login, many people Claude Code, Codex, and GitHub Copilot CLI are logged in once, as the server's OS user. Every team member's sessions run under those logins; Cogpit records who started what. That is the model — it is not per-user credential isolation.

02Quick start

The five-minute version. Read Deploy properly before you let anyone else in.

  1. Install at least one supported CLI on the server — Claude Code, Codex, or GitHub Copilot CLI — and log in. Cogpit drives those CLIs — it has no models of its own and needs no API keys.
  2. Build Cogpit. 
    git clone https://github.com/gentritbiba/cogpit.git
cd cogpit
bun install
bun run build
  3. Start it in team edition, bound to loopback. 
    COGPIT_EDITION=team bun server/standalone.ts
    The boot log tells you the edition, the address, and — on a fresh box — the URL to create the first admin.
  4. Put TLS in front of it. Browser logins need HTTPS; see below. A Caddy one-liner is enough.
  5. Open the HTTPS URL and create the founding admin. Then add your team from the users API.

03Deploy properly

HTTPS is not optional

Cogpit keeps the browser session in a __Host-, HttpOnly, Secure, SameSite=Strict cookie. A Secure cookie cannot be issued over plaintext, so a plain http://ip:19384 URL cannot log anyone in, by design — including the first-admin bootstrap, which now refuses up front rather than creating an admin you can't log in as.

# Caddyfile — terminates TLS, proxies to the loopback listener
cogpit.yourcompany.com {
    reverse_proxy 127.0.0.1:19384
}
nginx users Set proxy_buffering off; or session timelines will freeze and arrive in lumps — Cogpit streams over SSE. Your proxy must also forward X-Forwarded-For / Forwarded and X-Forwarded-Proto.

Run as a dedicated OS user

This is the real security boundary. Because every agent runs as the server's OS user, that user's filesystem access is your blast radius. Give it a home of its own, the work directories it needs, and nothing else.

# /etc/systemd/system/cogpit.service
[Unit]
Description=Cogpit Team
After=network-online.target

[Service]
Type=simple
User=cogpit
WorkingDirectory=/opt/cogpit
Environment=COGPIT_EDITION=team
Environment=COGPIT_HOST=127.0.0.1
Environment=COGPIT_DEVICE_NAME=team-box
ExecStart=/usr/local/bin/bun server/standalone.ts
Restart=on-failure

[Install]
WantedBy=multi-user.target

Environment

VariableDefaultDoes
COGPIT_EDITIONpersonalSet team to enable multi-user mode. Honored by the standalone server only.
COGPIT_HOST127.0.0.1Bind address. Team edition does not require a network password to bind wider.
COGPIT_PORT19384Bind port.
COGPIT_DATA_DIR~/.config/cogpitConfig and the team/ directory (accounts, sessions).

You can also set "edition": "team" in config.local.json. The environment variable wins when they disagree. A typo in either — "TEAM", "enterprise" — boots personal and logs a warning rather than failing silently.

Back up

Everything team edition owns lives in one place, all owner-only:

<dataDir>/
  config.local.json      # edition, paths, settings
  devices.local.json     # hub devices
  team/
    users.json           # accounts (scrypt hashes)
    sessions.json        # login tokens, hashed — survives restarts

04First boot & the founding admin

With zero accounts, the server prints a one-time setup URL. Its #bootstrap=... fragment contains a random process-local credential; the browser removes it from the address bar and sends it as X-Cogpit-Bootstrap-Token. Opening that exact URL gives you a create-the-first-admin page instead of the login form — you pick a username and password, and land signed in as an admin. Then the bootstrap closes for good — restarts do not reopen it, and a second attempt gets 410 Already bootstrapped. Restarting an empty server rotates the token.

Team edition: no users yet.
Open http://192.168.1.42:19384#bootstrap=<one-time-token> to create the first admin.
Browser logins need HTTPS: put a TLS proxy in front and open that address instead.

Set COGPIT_PUBLIC_URL and the banner names your real address — Open https://cogpit.yourcompany.com#bootstrap=<one-time-token> to create the first admin. — with no reminder attached, because that URL already terminates TLS.

Prefer curl? Set COGPIT_BOOTSTRAP_TOKEN before starting the empty server, send it in the setup header, and the endpoint hands back a bearer token:

curl -X POST https://cogpit.yourcompany.com/api/team/bootstrap \
  -H 'Content-Type: application/json' \
  -H "X-Cogpit-Bootstrap-Token: $COGPIT_BOOTSTRAP_TOKEN" \
  -d '{"username":"gent","password":"a genuinely long passphrase","displayName":"Gent"}'
Race-safe by construction Only a holder of the process-local setup token can enter the race. Concurrent valid attempts are serialized: exactly one admin is ever created, and every loser gets a clean 410. If the accounts file is ever corrupt or unreadable, the server refuses to start rather than booting into a state where bootstrap looks open again.

05Roles & capabilities

Two roles. Every gate is enforced on the server; the UI simply hides what you cannot use, so a member never stares at a button that 403s.

Run agent sessionsYesYesThe point of the product.
All permission modesYesYesMembers are trusted operators, not tourists.
Built-in terminal (PTY)YesNoA raw shell on the box as the shared OS user — the biggest escape hatch.
Host files, exact transcript diffs, undo, and scriptsYesNoThese expose absolute paths or exact before/after content and are not yet confined to server-owned workspaces.
Inspect or edit server / MCP configYesNoDefinitions can contain bearer tokens, headers, and command environment secrets.

Today, everyone sees the same sessions Roles currently gate machine access, not visibility. Per-user session ownership, workspaces, and sharing land in the next phase — see What's next. Deploy accordingly: this is a trusted-team tool right now, not a client-isolation boundary.

Under the hood every route group carries a declared policy, and CI fails if a new endpoint forgets to declare one. Unlisted paths default to admin-only, so the failure mode of forgetting is "locked", never "wide open".

06Managing users

Admin-only, over the API. A management UI is a later phase. All examples assume you are logged in as an admin (see Logging in for how to get $TOKEN).

Create an account

curl -X POST https://cogpit.yourcompany.com/api/team/users \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"username":"maria","password":"another long passphrase","role":"member"}'
FieldRules
usernameLowercase, 2–32 chars, a-z 0-9 . _ -. Normalized on the way in.
passwordMinimum 16 characters. Stored as a versioned scrypt hash (OWASP profile).
role"admin" or "member".
displayNameOptional, trimmed, capped at 64 chars. Defaults to the username.

List accounts

curl https://cogpit.yourcompany.com/api/team/users \
  -H "Authorization: Bearer $TOKEN"

Password hashes are never serialized — the response is an explicit allow-list of public fields.

Disable, promote, or reset a password

# Someone left — cut them off right now
curl -X PATCH https://cogpit.yourcompany.com/api/team/users/u_9f2c1a4b \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"disabled":true}'

# Promote
  -d '{"role":"admin"}'

# New password
  -d '{"password":"a replacement long passphrase"}'
Changes take effect immediately Disabling a user, changing their role, or resetting their password revokes that person's live sessions on the spot — no waiting for a token to expire. Mixed updates are all-or-nothing: if any field is invalid, nothing is applied.

You cannot disable or demote the last remaining enabled admin — the server refuses with a 400 rather than locking everyone out of their own box.

Who am I?

curl https://cogpit.yourcompany.com/api/me -H "Authorization: Bearer $TOKEN"
{
  "authenticated": true,
  "edition": "team",
  "user": { "id": "u_9f2c1a4b", "username": "maria", "role": "member", ... },
  "capabilities": { "terminal": false, "configWrite": false, "hostFiles": false, ... }
}

This is what the UI gates itself on. Personal edition returns full capabilities and a null user, which is why the same renderer serves both editions unchanged.

07Logging in

People

Open the HTTPS URL. The login screen shows a username field in team edition and password-only in personal — it asks the server which it is. The session lands in an HttpOnly cookie that JavaScript never touches.

Scripts and agents

Machine clients use one Bearer round-trip and get a token back. Username and password are separated by the first colon — passwords may contain colons.

TOKEN=$(curl -s -X POST https://cogpit.yourcompany.com/api/auth/verify \
  -H "Authorization: Bearer maria:another long passphrase" \
  | jq -r .token)

curl https://cogpit.yourcompany.com/api/projects -H "Authorization: Bearer $TOKEN"
Session ruleValue
Absolute lifetime8 hours
Idle timeout30 minutes
Survives a server restartYes — tokens are stored hashed, and role changes re-apply on restore
Failed-login rate limit5 per minute, per client
Wrong password and unknown user look identical Both return 401 Invalid credentials and both do the same cryptographic work, so the login endpoint can't be used to enumerate who has an account. A disabled account only reveals itself after the correct password.

08Driving it from your desktop app

You do not have to live in a browser tab. Your existing personal Cogpit can add the team server as a device and drive it from the app you already use.

  1. Devices → Add device in your desktop Cogpit.
  2. Enter the host — https://cogpit.yourcompany.com for a TLS-fronted box.
  3. Enter the username and password of the team account to connect as. A live probe tells you immediately whether it is reachable, whether the credentials work, and whether the account is disabled.
  4. Switch with ⌘⇧1–9, cycle with ⌘⇧0.

Give each hub a team account of its own rather than reusing a person's: that password is stored on the hub machine, and a dedicated account can be disabled or rotated without cutting anybody's browser session.

Everything you do through the hub acts as that account. Connect as your admin account and you see everything; connect as a member and you get exactly a member's surface. Your browser never talks to the team box directly — the hub proxies, and the stored credential never reaches the front end.

Machine-local actions are hidden while remote Open-in-editor, reveal-in-folder and open-terminal would act on the server, so they disappear when a remote device is selected. Copy-path is offered instead.

09Agents, hooks & MCP

MCP connectors

Configure your connectors once on the server, as the Cogpit OS user. Everyone's sessions inherit them — that shared connector pool is a large part of why a team box is worth running. Connector definitions and the per-session selector are admin-only because definitions may contain bearer tokens, headers, and command environment secrets.

Agent hooks keep working

Notifications are raised by Cogpit's own session activity monitor — no agent hooks and no unauthenticated ingest endpoint. The notification inbox at /api/notifications requires a logged-in user like any other API.

Other agents driving Cogpit

The external session API is unchanged; it just needs a token now. Same endpoints as always:

EndpointDoes
POST /api/create-and-sendStart a session with a first message
POST /api/send-messageFollow-up turn in an existing session
POST /api/stop-sessionStop a running session
GET /api/projectsList projects and their dirNames

10Security model, stated plainly

What is actually enforced

  • Every request authenticates as a named user. No local bypass, no shared password.
  • Passwords: 16-character minimum, versioned scrypt on the OWASP profile. Login tokens are stored as SHA-256 hashes — the raw token never touches disk.
  • Every route group declares an access policy; unlisted paths are admin-only by default and CI blocks a route that forgets to declare one.
  • The terminal is admin-only at the WebSocket upgrade itself, not just in the UI; established standalone, hub, and Vite-development PTY sockets and authenticated live HTTP streams are closed on logout, disable, demotion, or expiry.
  • A failed team identity lookup stays zero-capability; it never falls back to the personal-edition admin surface.
  • Disable a user and their sessions die immediately, everywhere, including through the hub. Absolute and idle expiry survive restarts.
  • Cross-site request screening on every mutation, including the unauthenticated hook and bootstrap paths.
  • Account files are owner-only; a corrupt accounts file stops the server instead of degrading into an open state.

What is not there yet

  • No per-user session isolation. Every member can see and drive every session on the box today. Phase 2.
  • No audit trail. Who-sent-what logging is Phase 3.
  • No agent sandboxing. Cogpit surfaces the CLI's own approval prompts; it cannot sandbox what the CLI cannot. Members can still ask an agent to read anything the OS user can read — which is why the dedicated OS user matters more than any role gate.
  • No security audit or pentest. This is one team's threat model, reviewed adversarially but not professionally assessed.
Do not expose this directly to the internet Put it behind Tailscale, WireGuard, or a Cloudflare tunnel with access control, and treat it as the most sensitive service on that network. It runs agents with real filesystem access.

11Troubleshooting

12What's next

Team edition ships in phases. This guide documents Phase 1, which is complete and deployable.

  • Phase 1 — Core ✓ — editions, accounts, authentication, roles, policy enforcement, hub user-auth, capability-gated UI.
  • Phase 2 — Workspaces & visibility — admin-curated project directories assigned to people, session ownership, members see their own plus what's shared, path scoping on the file APIs.
  • Phase 3 — Sharing, audit & usage — share a session to a teammate (view or full handoff), a full-fidelity record of who sent what, per-member token and cost APIs.
  • Phase 4 — Plugins — a typed extension surface so a fork can add its own views, timeline renderers, and one-click flows (an SEO suite, a client-reporting suite) without diverging from upstream.
  • Phase 5 — Admin UI — users and workspaces panels, an audit browser, and a usage dashboard, replacing today's curl commands.
